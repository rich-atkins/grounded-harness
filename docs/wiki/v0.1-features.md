# grounded-harness v0.1 — what it is, and how to read it

grounded-harness is an agent harness where evaluation is a runtime property: every run evaluated, every run resumable, every gate able to fail. It merges two earlier starters ([agent-eval-starter](https://github.com/rich-atkins/agent-eval-starter)'s eval-gate pattern, [resumable-llm-pipeline](https://github.com/rich-atkins/resumable-llm-pipeline)'s run discipline) with lessons measured out of a production pipeline migration and a judge-panel validation harness.

## Three rules, enforced in code

**Unknown is not zero.** Missing token counts are recorded as null, and a cost ceiling that cannot verify spend refuses to continue ("unverifiable budget") rather than treating unknown as free.

**Evidence floors.** The trajectory gate refuses to PASS on fewer than three goldens: an aggregate over too little evidence says `insufficient`, never a confident number.

**Every gate can fail, provably.** The demo ships two sabotage modes and CI runs both: a broken tool must turn the gate red, and a thinned sample must trigger the refusal. A sabotaged demo that passes fails the build.

## The pieces

| Surface | What it guarantees |
|---|---|
| Loop + providers | deterministic `MockProvider` (scripted turns) and a lazy `AnthropicProvider` behind one seam; the whole harness tests offline with no keys |
| Toolbox + MCP bridge | tools are code with schemas; any stdio MCP server's tools mount directly, with MCP-level errors surfaced as tool errors, never as content that reads like an answer |
| Budgets | step ceilings stop spend BEFORE it happens; cost ceilings settle AFTER the paid step is recorded, so no paid turn goes unrecorded; runs end gracefully with honest partial summaries |
| Checkpoint/resume | atomic writes; resume replays completed steps without re-executing or re-billing; resume against changed inputs is REFUSED (a refused resume costs a re-run, a wrong resume costs correctness) |
| Roles | planner → parallel workers → critic, with structured hand-offs via tools: a plan that was never submitted through `submit_plan` is not a plan; a budget-exhausted worker is honest partial work the critic judges, not a team failure |
| Trajectory evals | record a run as a golden; replay it with scripted model turns and REAL tool execution; judge four families (tool-correctness, loop-efficiency, groundedness, budget-adherence); gate on absolute bar or committed baseline |
| Telemetry | one JSONL line per model turn (single choke point), optional OpenTelemetry view |

## The demo (offline, no keys)

`grounded-harness demo` runs a scripted agent over a vendored copy of grounded-mcp's ACME vault through a REAL grounded-mcp server on stdio, replays three goldens, and gates. `--sabotage broken-tool` makes the vault evaporate mid-read (groundedness goes red, exit 1); `--sabotage thin-evidence` replays one golden (the gate refuses, exit 1). The vault is vendored so the demo works from any install and the goldens stay stable against upstream edits.

## Found during its own build (the receipts)

The budget tests caught the loop discarding a PAID provider turn unrecorded under a tight step ceiling (fixed: pre-flight step checks, post-record cost checks). And the MCP bridge's first integration test found a real bug in grounded-mcp v0.1 itself: every DB-touching tool call failed over real MCP transport (worker-thread SQLite), invisible to that project's in-process eval suite. Fixed upstream as v0.1.1 the same hour. Integration-level evals earn their keep before v0.1 ships.

## Honest boundaries

The mock provider is deterministic by design, which means golden replay regression-tests the harness, the tools and the tool data, NOT the model: model-quality evaluation needs live runs and judges (the pattern exists in this family's history; wiring it here is future work). Groundedness in v0.1 is substring containment, deliberately: measurable and cheap, but it cannot catch paraphrased unsupported claims. One provider ships beyond the mock; the seam is the invitation.
